# 管理端错误反馈、加载与拆分设计

**状态：** Implemented and verified

## 目标

让内容运营后台的写操作具备可观察的成功、提交中和失败状态；让互不依赖的首页读取并发执行；在不重写页面数据计算和既有业务 API 的前提下，按业务域逐步降低大组件耦合。

## 设计决策

### 1. Server Action 状态

- `apps/web/app/(admin)/admin/actions.ts` 的写 Action 返回 `{ ok, message }`，成功消息只在下游 API 成功且路径重验证完成后返回。
- 后端错误优先解析 JSON `detail`，兼容 Pydantic 错误数组；无法解析时截断普通错误文本，单条最多 280 字符。
- 不把请求头、管理 token、Prompt 或原始敏感上下文放入状态；不在客户端打印异常堆栈。
- `AdminActionForm` 使用 React 19 `useActionState`，在原生表单边界显示提交中状态和 `role="alert"` 失败消息；成功消息也只来自 Action 返回值。
- GET 筛选与图片建议链接继续使用普通导航，不混入写操作状态机。

### 2. 后台首页并发加载

- 审核队列、展示配置/图片建议、榜单引用、摘要、正文、相关推荐、智能分析配置、媒体事件和按用户权益查询互不依赖，使用一次 `Promise.allSettled` 并发启动。
- 每个结果仍由原有分区错误文案接管；一个请求失败不会丢弃其他成功模块。
- 展示配置成功后才决定图片建议的 fallback 文案，但图片建议请求本身与其他首页请求并发发起。

### 3. 渐进拆分边界

- 第一批只移动“内容质量编辑表单”（摘要、正文模块、相关推荐、榜单引用）到 `content-quality-forms.tsx`。
- 页面布局、排序/缺口计算、API client 和写 Action 不在本批次重写。
- 后续审核、媒体和轮换域各自单独移动，每次移动后必须复跑相应组件测试与 typecheck。

## 非目标

- 不引入表单状态库、Toast 依赖或新的运行时依赖。
- 不改变后台 API 契约、权限边界、缓存策略和已有业务数据。
- 不把所有 3000 行 Dashboard 一次性拆成多个页面，也不借机修复无关 UI 文案或图片优化警告。

## 验收

- Action 错误回归能收到后端 `detail`，表单能显示失败原因；成功路径继续调用既有 `revalidatePath`。
- 后台页面、Dashboard、Action 定向测试通过，Web typecheck/lint/全量测试/构建通过。
- 页面大组件只减少一个业务域，内容质量表单测试和既有后台回归保持通过。
