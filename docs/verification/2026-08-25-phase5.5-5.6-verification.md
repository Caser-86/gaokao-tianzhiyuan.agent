## Phase 5.5: local smoke evidence

The WeChat smoke fixtures previously reused one plaintext `nonce` for several
different callbacks. After replay protection was enabled, that correctly made
the second callback look like a replay. The fixtures now generate a distinct
signed URI for each plaintext callback while keeping the runtime timestamp
fresh.

Verified with a new local SQLite database and synthetic values only:

```powershell
powershell -ExecutionPolicy Bypass -File scripts/start-local-stack.ps1 `
  -AdminToken '<synthetic-admin-token>' `
  -WechatOfficialAccountToken '<synthetic-wechat-token>' `
  -WechatOfficialAccountAppId '<synthetic-app-id>' `
  -WechatOfficialAccountEncodingAesKey '<43-character-synthetic-aes-key>' `
  -SmartAnalysisMode off `
  -DatabasePath '.tmp/phase5-smoke-success.db' `
  -StateFilePath '.tmp/phase5-smoke-success.state.json' `
  -RunSmoke
```

Observed result:

- API and Web started successfully.
- The API `/version` probe returned the expected synthetic release value
  (`dev`) when called with `-ExpectedReleaseVersion dev`.
- Health, chat, Web, admin settings, chat message and generic WeChat adapter
  probes passed.
- Official-account URL verification passed.
- Plaintext text, subscribe, menu click, scan, picture, direct image, video,
  voice, location and link callbacks passed.
- AES URL verification and AES text callback passed.
- The focused `scripts/smoke-wechat-official-account.ps1` was also run against
  an independent local stack and passed the same plaintext/AES callback set.
- The stack was stopped with `scripts/stop-local-stack.ps1`; ports 8000 and
  3000 were confirmed free afterwards.
- A repeated-smoke regression was reproduced against the same persistent
  SQLite database: fixed callback nonce/MsgId values caused the second run to
  be acknowledged as a replay. The smoke script now adds a per-run identifier
  to every plaintext/AES nonce and MsgId. The focused dry-run regression test
  passed with two different verification nonces.
- A synthetic three-stage local rollback rehearsal on the same SQLite database
  then passed: `release-old` full smoke, `release-new` full smoke, and
  `release-old` full smoke after rollback. The final direct `/version` response
  and the saved stack state both reported `release-old` before the stack was
  stopped and ports were released.
- The independent `smoke-wechat-official-account.ps1` was also run twice
  against one persistent SQLite stack; both plaintext and AES probe sets
  passed on both runs with different run-scoped nonces.

This is local pre-deploy evidence. It does not prove a production deployment,
HTTPS setup, monitoring, public release version ownership or rollback.
